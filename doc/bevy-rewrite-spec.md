## 一、项目定位

**一句话**：一个俯视斜角的自动战斗刷子游戏。玩家化身游戏世界的主角，通过组织队伍、分配装备、派遣多路兵力，在世界地图上持续刷怪、解锁更高价值区域，把战利品转化为更强的 build。

**灵感参照**：
- 《暗黑 2》：长期刷装备、逐步进入更高价值 farm 区域
- 魔兽地图 / 塔防：观战、编组、分兵、自动执行
- 《三国无双》：战斗本身的演出爽感
- 《上古卷轴 5》：主角动机不预写死，由玩家在行动中定义

---

## 二、玩法核心循环

```
世界地图选择区域 + 兵力投放
  → 派遣主角和/或队友分路出击
  → 自动战斗持续刷怪
  → 打不过则自动返营
  → 战利品入库
  → 基地内整理装备、打造、重新编组
  → 再次派遣
```

**节奏特征**：强调中长循环，不强调微循环。玩家的乐趣不是连续点击，是配置 + 观察 + 转化。

## 三、玩法系统清单（target）

每个系统标注 **必做** / **后期** / **可选**，以及"做什么 / 不做什么"。

### 3.1 战斗（必做）

- 玩家**不直接手操**移动 / 普攻
- 玩家战前配 build、阵容、编组、AI 策略
- 战中以观察 + 少量高层介入为主
- 爽感来源：命中反馈、死亡表演、群体清场、大招时刻、观战满足
- 爽感曲线：前期偏惊险（关心血线），后期偏收割（关心范围 + 联动）
- 失败必须可读——玩家能看懂"为什么输了"
- 失败代价：进度受阻 + 资源损失，**不**强调一次性吐干净所有积累

**不做**：
- 伤害数字飞屏作为主反馈
- 满地掉落乱飞作为主反馈
- Roguelike 三选一 build

### 3.2 单位与角色（必做）

- 主角（沉默型空白主角，玩家化身）
- 队友（伙伴型，半固定职业，初始倾向 + 分支培养）
- 敌人（按区域和波次配置）
- 每个单位有：HP、能量资源（蓝/怒/气）、装备槽、技能槽、阵营
- 主角与队友的关系是组织关系：整体高服从、不做反抗 / 离队 / 人际撕裂戏

### 3.3 技能系统（必做）

- 每个角色多个技能槽（普攻 + 主动技能 + 终极技能）
- 普攻也是技能（统一管线）
- 技能有：冷却、能量消耗、施法时长、效果触发时刻、动画
- 技能形态多样：近战 box、远程投射物、群体效果、buff/debuff、光环、召唤
- 技能之间存在**联动**（设计目标），不只是各自独立
- 大招：长 CD 但带来明显高潮段

### 3.4 投射物（必做）

- 远程技能产生的飞行物（火球、箭、闪电链等）
- 飞行 + 命中检测 + 命中扣血 + 寿命管理
- 高速投射物**不能隧穿**（即使弹速 > 目标厚度 / 帧）
- 可能扩展：穿透、反弹、追踪、分裂

### 3.5 状态效果（必做，分阶段）

中后期会大量使用，初期可以只做基础几种：
- **CC**：眩晕、定身、击退、冰冻
- **DoT**：流血、燃烧、中毒
- **Buff**：增益（暴击率、攻速、护甲）
- **Debuff**：减益（降抗、易伤、虚弱）
- **光环**：跟随某 owner、范围影响周围单位、聚合 buff

### 3.6 伤害与抗性（必做）

- 多种伤害类型（物理 + 元素：火 / 冰 / 雷 / 毒 / 暗等，具体数量待定）
- 每种伤害对应一种抗性
- 暴击 / 命中判定 / 闪避（D2 风格）
- 命中表现：hit shake、喷血粒子、命中音

### 3.7 死亡 + 濒死 + 升华（特色机制，必做）

- HP = 0 进入**濒死**，不直接死亡。队友可救起或带走逃跑。
- 全员濒死 → 世界**暂停**，弹献祭框：
  - 接受死亡 → Game Over
  - 献祭一名队友 → 队友**永久死亡**（不可逆），主角**升华**，回满血，进入强化状态
- 触发升华还需要满足额外条件（持有"霸王之卵"等稀有道具，具体待定）
- 升华次数 / 形态 / 是否可逆：待定

### 3.8 AI 系统（必做）

玩家不直接手操，但仍是主角——**通过 AI 配置表达意志**。

**默认 AI 行为**：派去某区域 → 一直刷 → 打不过自动回家。玩家手动取消才主动召回。

**可配置维度**（动作集合封闭，玩家组合而非编程）：
- 阈值：血量回家、逃跑距离、拾取价值线
- 优先级：精英怪 vs 普通怪、拾取 vs 战斗、自保 vs 救人
- 动作启停：例如"主角永不主动逃跑"、"盗贼禁止主动接战"
- 长期目标：例如"凑齐 1000 金"、"刷出某件装备"

**核心控制杆**：**风险承担值**（保守 ↔ 激进）。一个滑块决定撤退阈值，统一替代"侦察 / 正式"两套规则。同区域同怪，收益差异来自玩家选择的行动风格深度。

**复杂度上限**：简单反应式 AI（FSM 即可）。少数特别复杂的决策可考虑 GOAP（plan + memory + interrupt），但是少数。

### 3.9 多路出兵（必做，中期）

- 同一批总兵力可自由编组（4、2+2、1+3、最多 4 路各自为战）
- 多路同时进行，本质是**兵力投资**而非多任务系统
- 所有路线核心玩法都是打怪——不做护送 / 采集 / 救援 / 拖延 / 复杂脚本
- 路线之间不连锁：一路打不过自动停 + 回家，其他路线继续
- 主角自由站位：亲自带一路 / 去另一路 / 坐镇后方 / 只调度

### 3.10 世界地图 / 区域（必做，中期）

- 外层结构是**世界地图 + 区域推进**，不是菜单选图
- 基地是世界中的后方据点
- 不同区域逐步从未知变熟悉的 farm 点
- 主目标：解锁更高价值刷图区，最终进入 end game
- 区域信息：初见半透明（大概风险 + 产出方向），打过一次后**公开透明**
- 不做侦察 / 情报 / 探子系统
- 地图结构固定，每次进入怪群组合、波次有小随机
- 区域有**危险等级**，派遣前可见
- 各区域有不同**材料产出方向**

### 3.11 装备系统（必做，必为 end game 服务）

- 装备归主角所有，主角拥有最终分配权
- 队友穿戴的装备是主角发下去的军需 / 赏赐
- **词缀浮动 + 数值浮动**
- 独特装备分层：普通极品 / 完美极品 / 传说完美品
- 长期目标是**凑齐完美品**，不是仅仅获得
- 独特装备之间存在 build 联动
- 不同高价值区域产出不同方向的极品
- 后期可加：游戏内展示系统（陈列完美品 / 成套收藏）

### 3.12 战利品 / 仓储（必做，中期）

- 战利品默认**先入库**，不强制打断结算去比较装备
- 战利品 = 装备 + 材料 + 金币
- 仓储是基地的核心功能之一
- 不强调满地乱飞的视觉戏

### 3.13 基地（必做，中期）

**定位**：后勤 + 轻建设据点。**不**发展为独立经营游戏。

**功能优先级**：
1. 装备与仓储
2. 打造与生产
3. 队伍管理与编组
4. 恢复与复活

基地操作**也消耗时间**（世界时间继续推进），换装 / 打造 / 恢复都不是免费动作。

### 3.14 时间系统（必做）

- **全局单一时间线**——不存在多路时间不同步，不存在"单独快进某一路"
- 多路出兵 = 多个视角共享同一时间推进
- 时间是**周转成本**，不是倒计时压力
- 任何动作都消耗时间：战斗、旅行、基地操作、决策本身
- 时间不能把玩家锁进"纯等待"——等待期可以有轻收益但不能压过战斗本身

### 3.15 视图层（必做）

**多 monitor 分屏**：玩家面前是一屏多 monitor 的"监控室"——每台 monitor 可独立看一个战场镜头，便于"上帝式总览多路"。

- 单 / 双 / 三 / 四 分屏可切换
- 每个 monitor 接一台独立 camera
- camera 可跟随单位 / 锁定固定位置
- 同一 camera 可被多 monitor 显示

### 3.16 表演与反馈（必做）

- **命中反馈**：受击 hit shake、喷血粒子、命中音、停顿感
- **死亡表演**：不同敌人不同死法，Boss 死亡尤其要场面
- **群体清场**：成片敌人被扫掉的视觉效果
- **大招时刻**：长 CD 带来高潮段（视觉特效 + 音效层次）
- **过渡节奏**：打完一波后的休整、生火、吃药、轻量对话，给刷怪过程"段落感"

### 3.17 触发区（必做）

世界中可放置矩形区域，单位进入 / 离开 / 持续接触时产生事件。用途：
- 切场 portal（踩进 → 切到下一区域）
- AOE 持续效果
- 拾取区
- 剧情触发

### 3.18 阵营 / 敌我（必做）

- 单位有阵营 tag：玩家方 / 敌方 / 中立
- 决定"谁能打谁"
- 投射物的阵营继承自发射者

### 3.19 角色定义（必做）

- 每个角色类型一份**蓝图**：speed / max_hp / max_mana / 技能槽配置 / 贴图集 / body 尺寸 / 阵营 / 初始 AI 行为
- 同类型角色共享蓝图，运行时各自有独立状态
- 蓝图是数据，应能在不重新编译游戏的情况下调整（设计目标——具体形式待定）

## 五、明确的非目标

写在这里防止后续"顺手"加上。

- ❌ Roguelike 三选一 build / 局内随机
- ❌ 赛季 reset / 一次性通关 Boss
- ❌ 大量对话分支 / 重剧情 CRPG
- ❌ 复杂忠诚 / 道德 / 浪漫系统
- ❌ 多人联机 / 在线对战
- ❌ 重经营模拟（基地是后勤而非主玩法）
- ❌ 沉浸式 ARPG 手操（玩家不直接控制每帧动作）
- ❌ 大量瞬移 / 传送门便利机制（必须有世界内解释）
- ❌ 时间倒计时压迫 / 限时事件作为主玩法
- ❌ 主角永死 / 队友随便就永死

## 六、合理性原则（贯穿设计）

- **世界内自洽**：系统可以抽象，不能出戏。便利机制必须有世界解释（马车 / 商队 / 信使等）
- **强度层级稳定**：普通人不应与主角团同强
- **倒下有代价但非永死**：HP = 0 是濒死不是死亡；死亡（永久）只在玩家明确选择献祭时发生
- **失败可读**：玩家能从战况看懂为什么输

## 七、技术约束

| 维度 | 取值 |
|---|---|
| 观感 | 俯视斜角 |
| 视觉风格 | 全 2D sprite（角色 / 怪物 / 植被 / 建筑 / 道具 / 特效），参考饥荒 |
| 引擎空间 | 3D 世界（XZ 平面为地面，Y 为高度），sprite 用 Y 轴 billboard |
| 渲染补充 | 自定义粒子 + 几何特效（闪电等），blob shadow decal 替代真实投影 |
| 分辨率 | 2560×1440（demo 默认），最终支持窗口缩放 |
| 目标帧率 | 60 FPS |
| 模式 | 单机（无多人联机） |
| 主要平台 | Windows（先），Linux / macOS / wasm 可选 |
| 同屏战斗规模 | **待定**（影响性能预算）：保守目标 50-100 单位，期望目标 200+ |
| 输入 | 键盘 + 鼠标（手柄可选，不优先） |

## 八、Bevy 重写前需要决定的开放问题

不需要全部决定才开工，但越早定越好：

1. **资源加载策略**：编译时嵌入（保证零外部依赖发布）vs 运行时加载（支持热重载和资产工作流）vs 两者混合
2. **多场景实现方式**：多路出兵需要多个并行世界——用一个全局世界 + 实体标签过滤，还是真的开多个独立世界？
3. **物理库选型**：用现成的 2D 物理库（碰撞 + 推开 + sensor 命中），还是自己写最小够用的？
4. **同屏战斗规模**：决定空间索引 / 物理性能 / spatial query 的预算
5. **脚本 / mod 支持**：未来是否要让脚本作者（设计师 / mod 玩家）在不重编游戏的情况下加内容？决定是否需要一层稳定 SDK
6. **平台目标**：是否一开始就考虑 wasm 浏览器分发（影响某些库的选择）
7. **调试工具优先级**：调参面板（vfx_lab 的等价物）是 Day 1 必需还是后期补
8. **存档格式**：决定数据结构是否需要"可序列化"作为一等约束

## 九、领域纯函数原则（编码纪律）

游戏逻辑分两类，按"能不能写成 pure function"切开。这条原则跨整个项目生效，无论 §八 的开放问题怎么决议。

### 9.1 判据

**这个函数能不能换一个 engine 直接复用？**

- 能 → 抽到独立的领域模块（暂定 `domain/`），作为 pure function。
- 不能 → 留在 system 函数体里，依赖 ECS。

判据等价于"不读写 ECS / 没有副作用"，但用"换 engine"作 thought experiment 更具操作性——立刻就能判断，不需要对纯函数概念有正式训练。

不需要真去换 engine。这只是判据，不是承诺。

### 9.2 抽到 domain 的（pure function）

特点：输入是当前快照数据，输出是新数据或决策。无副作用。

典型例子：

- 伤害计算 `resolve_damage(attacker, defender, weapon, crit) -> u32`
- 暴击 / 命中判定 `is_crit(rng_state, chance) -> bool`
- Buff 叠加规则 `stack(existing: &[Buff], new: Buff) -> Vec<Buff>`
- 装备词缀加成 `final_stats(base, equipment, buffs) -> Stats`
- XP / 等级曲线 `xp_for_level(level) -> u32`
- 战利品 roll `roll_loot(table, rng_state) -> Vec<Item>`
- AI 评分函数 `score_target(my_state, target_state) -> f32`

### 9.3 留在 system 的（ECS 操作）

特点：依赖空间索引、世界状态查询、entity 生成 / 删除、跨 entity 协调、`Res<Time>` 等引擎资源。

典型例子：

- "找最近的敌人"——要空间索引
- "spawn 一个 projectile"——要 commands
- "对范围内 N 个单位施加 buff"——要 query 多个 entity
- "AI 选目标"——查世界状态（**评分函数除外**，那部分是 pure 的）
- "推进 timer"——要 `Res<Time>`

### 9.4 类型 vs 函数（一处合理松弛）

判据应用到**函数**上，对**类型**可以放松：domain 类型允许挂 `#[derive(Component)]` / `#[derive(Event)]` / `#[derive(Resource)]` 等 Bevy trait derive。

```rust
// domain/combat.rs
#[derive(Component, Debug, Clone, Copy)]   // ← Component 是 Bevy
pub struct Health(pub u32);

pub fn resolve_damage(/* ... */) -> u32 { /* ... */ }   // ← pure function
```

严格说 `Health` 因为 derive 了 Bevy 的 trait 不算 engine-portable。但：

- 数据形状（一个 `u32`）是 engine-portable 的
- 操作它的函数是 engine-portable 的
- 换 engine 时把 derive 改一行就行

solo dev 这种松弛合理。如果将来 domain 真要拆 crate（例如喂给 wasm extension layer），那时再做"数据类型独立 / wrapper component"双份化。**现在不要为这个未来付双份成本**。

**为什么这个松弛安全**：锁定分层级，代价差一两个数量级。

| 层级 | 是什么 | 换 engine 的代价 |
|---|---|---|
| 行为锁定 | 函数体里 `Query` / `Commands` / `EventReader` | 重写每个 system |
| 架构锁定 | 设计哲学只能 ECS | 重新设计 |
| 类型锁定 | 一行 `#[derive(Event)]` | 一句 sed 替换完事 |

§9 原则的真实价值：把行为 / 架构锁定压到零，容忍类型锁定。这也是 Rust 生态的通行做法——serde / tokio / sqlx 任何一个集成都靠 derive，但没人说“我被 serde 锁定了”。

### 9.5 system 函数体的理想形状

三段式适配器：

```rust
fn xx_system(/* bevy args */) {
    // 段 1：从 query/event/res 取数据，转成领域类型
    // 段 2：调一个或多个 domain pure function
    // 段 3：把结果写回 commands/events/query
}
```

如果某个 system 写到 50 行还看不到 domain 函数调用，几乎肯定有领域逻辑没抽出去。这是 code review 的一个 trigger。

### 9.6 为什么坚持这条

不是为美。三个具体回报：

1. **可测试**：domain 模块不需要 `App` 就能 unit test。`#[test] fn crits_double() { assert_eq!(resolve_damage(...).damage_dealt, 20); }` 而已。
2. **可读**："战斗规则"和"ECS 数据搬运"分离后，读"战斗规则"时不被 `Query<&mut Health, Without<Invulnerable>>` 一类的样板淹没。
3. **可未来扩展**：抽出来的 pure function 直接就是将来 binding 给脚本（JS / wasm / Lua）的"动词"。今天 0 成本，将来 0 重写——即使最终没做 extension layer，前两条已经够本。

## 十、推进建议（不强制）

按"能跑出可见效果 + 渐进验证"的顺序：

1. 窗口 + 一只静态角色出现在屏幕上
2. 玩家移动 + 不穿墙 + 不穿敌人
3. 普攻命中扣血 + 敌人死亡 + 喷血反馈
4. 简单 AI（敌人追玩家 + 攻击）
5. 远程技能（投射物 + 高速不隧穿）
6. 多分屏视图
7. 多角色 / 阵营 / 多技能槽
8. 状态效果（先一种 DoT 验证管线）
9. 触发区 + 简单切场（一个 portal）
10. 多路出兵的最小可玩验证（两路同时刷）
11. 装备 + 战利品 + 仓储最小闭环
12. 世界地图 + 区域选择
13. 风险承担值 + AI 配置
14. 濒死 + 献祭 + 升华
15. 基地操作 + 时间系统
16. End game 完整体验

每一步**有可见效果 + 能跑 + 录屏对比**，否则不算完成。卡住就停下来评估，不要硬推。

## 十一、本文档的使用方式

- 这是 **What**（要做什么），不是 **How**（怎么做）
- 拿到新仓库后，**先**写一份对应的 ADR（架构决策记录），决定第八节的开放问题
- **然后**根据自己对 Bevy 的判断，自由设计 crate / 模块 / 数据结构 / 代码组织
- 现有 Zig 项目的代码可以**当参考资料**（特别是某些算法：扫掠命中检测、动画 phase 打散、闪电几何生成），但**不要直译目录结构和命名**
- 如果发现新设计跟本文档某条需求冲突，**先**讨论清楚再改文档，不要在代码里偷偷绕过
