# 单位制与资源规格 Cheatsheet

> 为什么游戏世界里有"1 单位 = 1 米"这种约定？怎么用它来找素材？PPI / PPM / 像素三者什么关系？

## 核心概念：Bevy 的 1.0 是啥？

引擎里的 `f32 = 1.0` **本身无单位**。`Vec3::new(5.0, 0.0, 3.0)` 就是坐标 `(5, 0, 3)`，引擎不知道也不在乎它是米、厘米、光年还是像素。

**"1 单位 ≈ 1 米"是整个 3D 生态的默契标准**，不是 Bevy 发明的。原因：

| 驱动力 | 为啥要按米 |
|---|---|
| **资源格式** | glTF / FBX / Blender 默认输出 1 unit = 1 meter。导入了直接用，不用 scale。 |
| **物理引擎** | Rapier / Avian 的重力 `-9.81`、密度、摩擦系数都按 SI 单位标定。1cm = 1 unit 的话重力要改 -981，全乱套。 |
| **光照 / 渲染** | PBR 参数、阴影距离、雾效默认都按米调。 |
| **跨引擎一致** | Unity / Unreal / Godot 3D 全是这样，减少切换摩擦。 |

**所以：选择 1 unit = 1 meter，是接受整个生态的标准化，不是凭空编的。**

## Percussion 项目的选择：32 PPM

### 定义

**PPM** = Pixels Per Meter

$$\text{PPM} = \frac{\text{sprite 像素高}}{\text{世界米数}}$$

我们定 **PPM = 32**，意思是：

- 1 米的角色 = 32 像素高的 sprite
- 比如 1.7m 人类 = $1.7 \times 32 = 54$ px  
- 比如 3m 树 = $3 \times 32 = 96$ px

### 为什么是 32？

| PPM | 像素高（人类） | 风格 | 缺点 | 代表 |
|---|---|---|---|---|
| 8–16 | 13–26 px | 极简 retro（FC / GBA） | 脸画不清 | Celeste, Stardew |
| **32** | **54 px** | **现代像素感** | **无** | **Eastward, HLD** |
| 64 | 109 px | 半矢量 | 不算"像素风" | Dead Cells |
| 100+ | 170+ px | 手绘 / 矢量 | 需要美术 | 饥荒 |

**32 PPM 的优势**：

- ✅ 免费素材多（现代独立像素风标准）
- ✅ 文件大小合理（1 米物体不会爆大）
- ✅ 动画帧数适中（不用 8x8 网格炸裂，也不会看不清）
- ✅ 混搭不同免费包也不容易崩比例
- ⚠️ 但不求 pixel-perfect（相机透视 + billboard 本身就是近似）

## 三个概念的区别

### 1. PPM（你的责任）

游戏设计层面定的约定。**你选一次，整个项目用这个尺子**。

- **决策点**：现在
- **改动成本**：高（所有素材都要重新筛选和调整）
- **代码体现**：常数 `const PIXELS_PER_METER: f32 = 32.0;`

### 2. Viewport 分辨率（引擎/操作系统）

游戏画面占多少屏幕像素（1920×1080、1280×720 等）。

- **决策点**：每个玩家的硬件
- **改动成本**：零（引擎自动适配）
- **code 体现**：`Window { primary_window { resolution: ... } }`

### 3. PPI（硬件，与编程无关）

显示器物理指标。那 1920×1080 个屏幕像素物理上多大。

- **决策点**：玩家硬件（24" 1080p vs 27" 4K）
- **改动成本**：不用改，玩家自己调看距离
- **代码体现**：无。游戏里完全不用管

### 链路图

```
游戏世界（米）
      │ × PIXELS_PER_METER（你决定）
      ↓
Sprite 像素（你的美术规格）
      │ [相机投影 + 3D 透视]
      ↓
屏幕像素（viewport 分辨率，引擎算）
      │ [OS DPI scaling / 显示器物理特性]
      ↓
物理英寸（显示器）
```

**关键**：你只管第 1 步。其他步骤让引擎和硬件处理。

## 素材筛选指南

### 第一步：确定目标尺寸

用 PPM = 32 换算：

**你想要的米数** → `目标像素 = 米数 × 32`

| 物体 | 合理米数 | 目标像素高度 | 搜索关键词 |
|---|---|---|---|
| 人类 | 1.6–1.8m | 52–58 px | `pixel character 48x64` / `top-down human` |
| 小怪（鼠、鸟） | 0.5–1.0m | 16–32 px | `pixel enemy 32x32` |
| 树（中号） | 3–4m | 96–128 px | `pixel tree 96x128` / `tileset` |
| 建筑（门） | 2.0–2.4m | 64–77 px | `pixel door 64x96` |
| 地表 tile | 1m（边长） | 32×32 px | `pixel tileset 32x32` / `CC0 ground` |
| 岩石（路障） | 0.3–0.8m | 10–26 px | `pixel rock 16x16` |

### 第二步：按许可证和格式筛

搜索参数（以 OpenGameArt / itch.io / Pixabay 为例）：

```
pixel character 48x64 cc0
"pixel pack" cc-by free
top-down tileset 32x32 license:cc0
```

**优先级**：
1. ✅ **CC0**（完全自由，推荐）
2. ⚠️ **CC-BY**（要署名）
3. ❌ **CC-NC / CC-ND / 不明**（避免）

### 第三步：验收尺寸一致性

拿到一个素材包后，检查：

```
角色列表：是否都在 48–64 px 范围？
动画帧：每帧尺寸是否一致？
地块：是否都是 32×32 或其整数倍（64×64 也行，但不混）
比例：角色头身比、树的粗细，是否视觉协调？
```

### 第四步：代码验收（"米制体检"）

Sprite 载入后，在代码里加一行注释：

```rust
// 人类角色：像素高 56px ÷ 32 PPM = 1.75m ✓
// 小树：像素高 96px ÷ 32 PPM = 3.0m ✓
```

如果算出的米数不合理（比如 0.2m 还当树），说明混淆了缩放基准，需要重新筛。

## 实战例子

### 案例 1：找角色 sprite

**目标**：1.7m 主角

1. 计算：$1.7 \times 32 = 54$ px
2. 搜索：`pixel character 48x64 cc0` / `top-down hero`
3. 找到包：48 × 64 / 56 × 64 的角色集
4. 验收：$56 \div 32 = 1.75$ m，符合（可接受±0.05m 误差）

### 案例 2：找地表 tile 包

**目标**：可铺地面，每格 1m

1. 计算：$1 \times 32 = 32$ px
2. 搜索：`tileset 32x32 cc0` / `pixel ground tile`
3. 找到包：32×32 grass / dirt / stone tiles
4. 验收：没混进 16×16 或 64×64，✓

### 案例 3：找建筑素材

**目标**：3m 高的树

1. 计算：$3 \times 32 = 96$ px
2. 搜索：`pixel tree 96x128` / `tree sprite cc0`
3. 找到包：但发现有 96px 有 128px 树（2.75m 和 4.0m）
4. 决策：分别标注米数在代码里，或者都调到 96px，保持一致

## Nearest Filter 的重要性

**必须设置**：所以素材 sprite 用 `ImageSamplerDescriptor::nearest()` 加载

```rust
// 错误（会糊）：
image.image_handle  // 默认 linear filter

// 正确：
// 在资源加载时指定 nearest filter
// TODO: Bevy 0.18 的 syntax
```

不用 nearest 的后果：

| Filter | 效果 | 适用场景 |
|---|---|---|
| **Linear** | 像素边界模糊 | 3D 写实 |
| **Nearest** | 边界锐利，色块清晰 | ✅ 像素风 |

## 常见踩坑

### 踩坑 1："找到个美术包，但没写分辨率"

→ 自己数像素。用 Aseprite / 画板 / 在线工具看图属性。或者按"视觉比例"反推：如果看起来比较细致，大概 64+ px；如果看起来粗糙，大概 16 px。

### 踩坑 2："这个 8×8 tile 包很可爱，但混了 16×16"

→ 不要混。选一个标准（32×32 推荐），所有资源都从这个起点 scale，不要在项目中部改主意。改动成本会很高。

### 踩坑 3："我找的角色 64px，树是 128px，他们能共存吗？"

→ 能，只要在代码里正确标注：

```rust
const CHARACTER_PPM: f32 = 32.0;  // 64px ÷ 32 = 2.0m
const TREE_PPM: f32 = 32.0;       // 128px ÷ 32 = 4.0m
```

只要 PPM 一致，不同大小的 sprite 会正确显示。

### 踩坑 4："相机一转，sprite 边缘就开始游泳"

→ 这是 3D + 2D billboard 的本质矛盾，无法完全避免。接受它，或者用路 B（固定相机）/ 路 C（低分辨率 RT）。
