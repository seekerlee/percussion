# Character AI 设计讨论总结

> 本文记录 AI 决策架构的设计逻辑，**与具体引擎实现 + 项目分层解耦**。文中提到的模块名（vocabulary / brain / goap 等）是概念性的，不预设落地为某一层或某个目录。

---

## 1. 核心需求

**挂机游戏**：玩家不在场，主角自动打怪、自动回家买药、自动回战场。
小怪 AI 走简单方案（BT/硬编码 FSM），**本文 AI 只关心挂机主角**。

不仅是"AI 自动玩"，而是**给玩家观看 + 调试**：
- AI 当前的"思考过程"（plan）给玩家看
- 玩家可调参数：血量阈值、逃跑阈值、攻击优先级
- 玩家可**派目标**：「收集 1000 金币」「升级到 Lv 10」，AI 根据自身知识自动找路径

→ AI 不是实现细节，是**核心玩法**。

---

## 2. 关键架构决策

### 2.1 AI 范式：GOAP（Goal-Oriented Action Planning）

**挂机主角用 GOAP，小怪用 BT / 硬编码 FSM。**

GOAP 在本设计的三个契合点：
- 行为涌现，新增 action 不动旧代码
- **无状态特性消解中断/恢复问题**：每次重规划只看世界，世界状态决定一切，不需要栈记忆
- 可作为玩法机制（plan 可视化 + 玩家调参 + 玩家派目标）

### 2.2 规划频率

业界（F.E.A.R. 等）用 **0.5-1 Hz + 事件触发重规划**。
单个主角规划，性能不是问题。

### 2.3 AI 视角 = 角色视角（关键洞察）

> AI 视角是游戏世界内角色的视角，这个角色不应该知道游戏实现细节。
> 角色的语言全部是描述这个世界的：视野内的怪物、NPC 的功能。

→ ports & adapters 模式。
→ 必须有一个 **vocabulary facade** 作为 AI 与游戏世界的契约。
→ vocabulary 中**禁止**暴露引擎实现类型（如 ECS 的 Entity 句柄、组件存储、位置分量等）。
→ 用脱壳数据 + 不透明句柄（如 `EnemyHandle`、`NpcHandle`，外部不可解构）。

---

## 3. 组件清单（草案）

**应用专属（针对本游戏）**：
- `vocabulary`：角色语言（脱壳数据 + 不透明句柄 + 函数签名，**不暴露任何引擎实现类型**）
- `knowledge`：用 vocabulary 表达的世界快照
- `actions`：Action 列表
- `goals`：Goal 列表
- `params`：玩家可调参数
- `brain`：Brain 实例化 + 装配
- `sense_system`：vocabulary “读”实现，把游戏世界翻译成 Knowledge
- `act_system`：vocabulary “写”实现，把 Plan 翻译成游戏世界中的动作

**可复用工具（与具体游戏无关）**：
- `goap`：facade + 反向 A* planner + Plan / Status / Cost 等类型
- `brain` 运行时：facade + `Brain<K, A, G>` 决策循环

> 命名先不改（vocabulary / Knowledge / Brain / Goal 等等待复盘）。

## 4. 6 个职责

```
┌──────────────────────────────────────────────────────────┐
│ ① 数据定义（"配置"）                                      │
│   Knowledge / Action / Goal / ParamProfile               │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│ ② sense_system: 游戏世界 → Knowledge                     │
│   把真实世界翻译成"角色感知"                              │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│ ③ planner（goap）                                        │
│   反向 A* 搜索；输入 Knowledge + Goal + Actions          │
│   输出 Plan = []ActionRef                                │
│   纯算法，零项目耦合                                      │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│ ④ executor（brain）                                      │
│   推进 Plan 当前步；管理 cursor；处理失败                 │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│ ⑤ act_system: Action → 游戏世界动作                       │
│   把 action 翻译成移动 / 施法等具体行为                    │
└──────────────────────────────────────────────────────────┘

横向贯穿：
┌──────────────────────────────────────────────────────────┐
│ ⑥ Brain System：协调以上 ② → ③ → ④ → ⑤                │
│   决定何时重规划（1Hz + 事件）                            │
│   选 Goal、持有 Plan、转给 executor                       │
└──────────────────────────────────────────────────────────┘
```

## 5. 待解决的问题

### 5.1 第一批 vocabulary API

待设计的清单，需要回答：
- 主角能"看到"什么（视野范围、记忆机制）
- 主角能"做"什么（动词列表）
- 不透明句柄设计（EnemyHandle / NpcHandle / WaypointHandle 等）

### 5.2 第一批 Action / Goal

依赖游戏机制清单（"6 问"未答）：
- 战斗（打怪给金币 / 经验？）
- 移动（地图有几个地点？家、商店、战场是同一个还是分散？）
- 物品（inventory？药水从哪来？）
- 经济（金币从哪来？怎么花？）
- 怪物刷新（自动刷？打完清场？）
- 触发条件（什么时候回家：血量？药数？固定时长？）

### 5.3 Knowledge vs PlanningState

A* 节点需要复制 Knowledge 副本（搜索时上百次）。Knowledge 包含视野中怪物列表等大数据，复制开销大。
**业界做法**：A* 节点只存"GOAP 关心的字段子集"——拆成 Knowledge（完整感知）+ PlanningState（规划用精简版）。
当前没决定要不要拆。

### 5.4 ParamProfile 字段范围

玩家第一版可调哪些参数？
- HP 阈值（什么时候喝药）
- 逃跑阈值
- 攻击优先级
- 全部？只挑核心几个？

### 5.5 plan 可视化

第一版要不要做 UI？还是先 console 看？

### 5.6 工程层面

- WorldState（Knowledge）的 hash/eql 实现策略
- A* 节点池 / arena allocator 选型
- 规划失败时如何"自我解释"（卡住原因展示给玩家）

---

## 7. 关键原则

1. **AI 是无状态的**（每次重规划只看世界），消解中断 / 恢复
2. **AI 视角 = 角色视角**（不应该知道游戏实现细节）
3. **GOAP 是核心玩法**，不只是 AI 实现（plan 给玩家看 + 玩家调参 + 玩家派目标）
4. **隔离铁律**：vocabulary 不允许暴露引擎实现类型；可复用工具（goap / brain）零项目耦合
